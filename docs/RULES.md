# xcblame: rule catalog (spec)

Status: draft v2, 2026-10-30 (review fixes per DESIGN Appendix B). Source of truth for `Rules/catalog.json` (DESIGN §7.1). Every record of the optimization catalog ([OC] = [research/research-optimizations-catalog.md](research/research-optimizations-catalog.md), records A1-G8) is carried over, deduplicated, and given a stable xcblame ID. Source IDs `S1`-`S55` refer to the [OC] source index. Other keys: [PP] dev-painpoints, [BP] build-pipeline, [DS] data-sources, [RL] real-log-inventory, [OBS-n] DESIGN Appendix A.

## 0. Legend

**ID prefix = category**: `SET` build settings ([OC] A), `SRC` Swift code level (B), `GRAPH` project structure/modularization (C), `PHASE` scripts and phases (D), `DEP` dependencies (E), `ENV` environment/Xcode prefs (F), `CI` CI-specific (G), `DYN` rules that exist only because of xcblame's own measurements (no [OC] record, no static signal). The number after the prefix equals the [OC] record number where one exists (SET-016 = A16). A new rule that belongs to a catalog category but has no [OC] record extends that category with a number above the catalog's highest (DEP-012). `info` in the Det column marks a docs-only entry: no detectable signal, shown in `rules explain`, never emitted as a finding.

**Det** (detection source): `S` static (project audit: pbxproj/xcproj, xcconfig, `-showBuildSettings -json`, schemes, manifests, defaults, machine), `D` dynamic (from build timings/log), `S+D` both (static finds it, dynamic sizes it).

**Apply**: `overlay(D)` / `overlay(R)` / `overlay` = line in `.xcblame/overlay-Debug|Release.xcconfig` (DESIGN §7.5). If a higher level shadows the key for the hook, the overlay lines stay and the finding offers, in order, `cli` (the `-xcconfig` wrapper on the xcodebuild command line, which sits above every project level and so is never shadowed: `xcblame verify --mechanism cli`, CI; probes-v0.6 Q1/Q3, v0.6 decision 2026-11-05), or `rec` for Xcode builds (remove the shadowing value by hand); never an automatic pbxproj edit; `cli` = xcodebuild argument or CI YAML snippet; `defaults` = `defaults write`, reversible, only with `fix --apply-defaults`; `scheme` = `.xcscheme` attribute (`--edit-project`); `pbxproj` = project edit (`--edit-project`, §7.6); `manifest` = Package.swift/Podfile edit (`--edit-project`, diff first); `rec` = recommend only (file:line, snippet, or steps); `+V` = applied only through `xcblame verify` (kept only if measurably faster); `measure` = A/B experiment only, never a fix.

**Impact band** (per build unless stated): `XS` < 1 s or < 2 %, `S` 1-5 s or 2-10 %, `M` 5-30 s or 10-30 %, `L` > 30 s or > 30 %, `?` unmeasured. When a dynamic measurement exists for the user's build, the band shown is computed from it and the catalog number below is context only. Basis in parentheses.

**Ev** (evidence tag from [OC]): `[P]` primary, `[S]` secondary with data, `[K]` unverified practitioner knowledge. **Every rule whose tag contains a [K] part (including mixed tags such as `[S/K]` or `[P]/[K]`) is gated as [K]: shown as "needs measurement", confidence `low`, never ranked above a measured finding, applied only with `+V`.**

**Cfg**: `D` Debug, `R` Release, `D/R` both, `CI` CI invocations only. Configuration names are matched by role (Debug-like: `-Onone` or `DEBUG` in `SWIFT_ACTIVE_COMPILATION_CONDITIONS`), not only by literal name.

**Confidence** is computed at runtime (DESIGN §7.1): high = mechanism tagged [P] AND cost measured on this build; medium = [S] with a measured cost, or [P]/[S] static-only; low = any [K] part. `doctor` (no build) therefore never shows `high`.

**Signal key**: each finding carries a `signalKey`; when several rules fire on one key the engine emits one finding and lists the others under "see also" (§10).
